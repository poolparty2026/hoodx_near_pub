## Security
- **M1 (code plus test).** `RULES_KEY_HEX` is never checked (main.ts:20, deliverer.ts:84-88, 128-129). A wrong or stale K (for example from another run.json) delivers anyway: creator paid, sale Released, `refund_key` refused, buyer holds a key that opens nothing. Fix: at startup and before each seal, read `get_config` and run `decryptRules(rules_ciphertext, K, strategy, rules_hash)`; refuse to start or deliver on failure. Test: a Deliverer built with a wrong K throws and sends nothing (also EC-K03).
- **M2 (trust assumption, D11/EC-K03).** Contract `deliver_key` accepts any 160-hex string (keys.rs:173-206). A compromised deliverer key, or a deliverer working with the creator, can take all escrow for garbage keys; a compromised host also leaks K. Not a code bug. The README and web copy must say the deliverer holds buyers' funds in escrow on trust (claims-checker). Possible mitigation (contract change, out of scope): a short refund window after delivery.
- Low: testnet guard is a substring check (main.ts:14, setup.ts:19; e2e.ts:16-20 has none), so `testnet.evil.com` and `https://x/?testnet` pass; allowlist exact hosts (`rpc.testnet.near.org`, `127.0.0.1`, `localhost`) via `new URL`; also check at startup with `view_access_key` that `DELIVERER_KEY` is function-call-only for `deliver_key`. Deadline uses host `Date.now()`, not block time, and delivery is sequential with FINAL waits, so up to 50 sales can miss the window (deliverer.ts:125-127). `DELIVER_GAS` 50 Tgas is unmeasured and README says 100 (chain.ts:10-11). Refunded sales still count toward `max_key_sales` (keys.rs:135-144), so a few accounts can fill the cap with low-order or unopenable pubkeys; the contract refuses only an all-zero key. Full-access keys for strategy/creator/platform in `.testnet/run.json` (setup.ts:35, 77-80): fine on testnet, add a header comment that it must not be reused for mainnet. `run.json` mode 0600 applies only on file creation (setup.ts:80): `chmodSync` after write. Byte API `seal()`/`open()` (seal/src/index.ts:64-77) lacks the pubkey length, all-zero and message-length checks and does not wrap libsodium errors in "SEAL:". e2e.ts hands the deliverer the plaintext rules key and puts all keys in one file; do not copy that layout to a real deliverer. Gas, helper URL `helper.nearprotocol.com`, `usdc.fakes.testnet`, `dclv2.ref-dev.testnet` and the `new` bounds are unverified guesses.
- Sound: transaction borsh layout and ed25519 signing, FunctionCall tag 2 with zero deposit, chain.ts can only build `deliver_key`; buyer and `buyer_pubkey` come from final-block views with a re-read; Released-after-failed-payout treated as delivered; `crypto_box_seal`, 160 lowercase hex, strict hex; pinned deps with integrity hashes; deliverer never calls `refund_key` or sends funds.

## Tests
- **H1.** EC-K02, K03, K04, K05 have no test and no ID; only the manual `scripts/testnet/e2e.ts` touches them, and it is not in CI. K03: a Deliverer with a wrong `rulesKey`; open the delivered key, check the hash, assert the mismatch text and the sale stays Released. K05: `tick` never sends after the deadline and `refund_key` still works. K02 (rekey) was cut by D57: mark the row not applicable in EDGE_CASES.md.
- **H2.** `inFlight` double-delivery guard untested (deliverer.ts:115-122): removing the check, the `delete`, or keying by the wrong id survives. Test two concurrent `tick()` calls with a blocking `deliverKey`: one send, second outcome skipped; a later tick is not blocked.
- **H3.** Deadline margin boundary untested (deliverer.ts:127): only `deadline-5` with margin 10; default 15 s never used. Test margin-1 (delivered), margin (skipped), margin+1 (skipped), and the default.
- **H4.** Testnet guard has no test (main.ts:15-17, 0% coverage). Extract it; test accept `rpc.testnet.near.org` and `http://127.0.0.1:<port>`, refuse `rpc.mainnet.near.org`, `testnet.evil.com`, `https://x/testnet`.
- Medium: M1 `signDeliverKey` checks the signature and "deliver_key" bytes only (receiver, nonce, args, gas, action tag); add a known-answer test against near-api-js. M2 page cap `limit: 50` untested at 49/50/51/0 sales. M3 window 0 and u64::MAX: BigInt does not saturate like the contract (keys.rs). M4 "Released counts as delivered" checks only state, not that `sealed_key` is ours; null re-read and Escrowed with `ok:false` untested. M5 EC-K06 tests thin: view returning a different `buyer` than the list (a `listed.buyer` mutant survives), duplicate buyer, no test that events are never read. M6 low-order key test asserts only "failed", not the reason or that nothing was sent.
- e2e (first-run audit): not a vitest test; the only balance check is `after > before` (e2e.ts:70) and `escrow_total` is printed, not asserted; no refusal paths (non-deliverer, deliver twice EC-C18, after the window EC-C137, refund before the window, refund after delivery EC-C62); `void createHash;` dead code; the deliverer key calling another method should fail. Seal: no external fixed test vector, no property tests, byte-API validation untested, prepended-junk test missing for the `^` anchor.
- Low: EC-C173..C178 mirrors are unnamed; no assertion that `rulesKey` is never logged (e2e.ts:45 echoes 300 chars of RPC error); `parseParams` accepts arrays; unused-import silencers.
