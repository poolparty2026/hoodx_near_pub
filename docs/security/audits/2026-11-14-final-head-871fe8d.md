## Medium

M1. Index reuse after a dropped exit record. remove.rs:67-79 (`drop_unproductive_exit`) pops the record, but `open_exit_action` (remove.rs:82) and `open_action` (trade.rs:346) take `index = actions.len()`. The popped exit already emitted an `action` event and an `action_result` event for index N (remove.rs:41, trade.rs:218). The next action (for example an agent `agent_close_position` in Running after an outsider's failing exit after the grace, or the next exit) emits a second `action` event with the same index N and a different op_id. Anything keyed by index (alerter, web, replay of events, a reader who saw the `Failed(read)` event for N) now sees one index with two histories, and `get_action(N)` shows the later one. Failure path: exit 1 fails (event index 5 Failed), exit 2 succeeds (event index 5 Ok); an event consumer that upserts by index shows the failure overwritten, or counts 2 actions for one slot. Fix: either keep the failed exit's record in a bounded ring (as the design already has for non-trading calls) or emit the drop explicitly (an `action_dropped` event with index and op_id) and document that index is not unique in events and op_id is the key. Add a test that two exits through the same index emit distinct op_ids and say so.

M2. A failed remove that opens the settle window drops its record. remove.rs:465 (`Failed("remove")`, window = true) is treated as unproductive (remove.rs:57 keeps only non-Failed). The comment at remove.rs:62-64 and the doc at remove.rs:462-463 say tokens might have moved, which is why the window opens, yet the only trace is two events. The check page and EC-R35 work from on-chain records; a payout-possible stage now has none, so a later disputed payout cannot be tied to an action. Not exploitable for funds (the window and margin still apply), but it contradicts "outcome unknown keeps its full record" in the doc comment. Fix: keep the record when `window` is true (that is, drop only when no payout was possible: all the `Failed("read")` and `Refused("position")` paths, which are window = false) or record `Failed(remove)` and drop only by the capacity rule. The test `failing_exits_leave_no_record_but_a_productive_exit_does` currently asserts the opposite for the failed remove (tests_remove.rs, "A failed remove: no record either") and does not assert that the window opened, so it pins the behaviour without noticing the conflict.
