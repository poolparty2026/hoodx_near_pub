## High (blocks the claim that the page verifies an agent run)

- **Decision hash mismatch (rules-verifier C1).** The agent's `decision_hash` is `sha256(stable({rules, state, decision}))` (`apps/agent/src/decide.ts:53-55`); the page hashes the published record text (`run.ts:263`, `checks.ts:34`, per `INTERFACE.md:145`). There is no shared helper in `packages/rules` (grep finds no `decisionHash`). Every action of an honest agent run would read "not matching". The fixtures hide it because `fixtures.ts:48,63` are built with the page's own hash. Same defect as `2026-11-12-code-agent-near-tx.md` H1/H2. Fix: one helper in `packages/rules`, in its own shared-interface pull request; add a test that feeds the real agent `round()` output to `checkRun`.
- **No test shows an out-of-rules action as "not matching" (test-auditor H-T1).** Replacing `const judged = worse(hashed, checkAction(...))` with `hashed` (`run.ts:158`) survives all 149 tests. Add a fixture whose decision text, hash and record agree but which `evaluate` would not produce; assert the exact row text and a "not matching" page verdict (proposed new ID EC-W30).
- **README claim "The check page and the agent judge actions with the same code" (README line 60/61, audit session's reading).** The evidence given is that both import `@poolside/rules`. But the agent never calls `withinRules` (agent audit, security M1 and test H) and hashes decisions with its own code, so the sentence is not yet supportable. Reword to what is true ("both import the rules package; the agent does not yet check its actions with `withinRules` and the decision hash is not yet shared") or fix the code first. A claim the code can't support is High under `SECURITY_PROCESS.md`.

## Medium

- **State is not rebuilt from public data (rules-verifier H1).** `run.ts:149` reads the guessed `fixture:market_state` view; only `state.block` and `state.point` are compared with the record (`run.ts:155`). `nowS`, `startedAtS`, `principal`, `holdings`, `fees`, `valuationPoint`, `confirmFromBlock`, `closedBy` are accepted as given, so a self-consistent invented state is judged "within the rules". The fixture is already inconsistent (`get_started_at` 900_000e9 s vs `startedAtS: 1_000`, `fixtures.ts:35` vs `:87`) and nothing flags it. Needs a MarketState builder from views (also in the web audit `2026-11-12-code-web-2.md`).
- **Refusals read better than "not matching" (security M1).** `run.ts:134-163`: refused, failed and swap-refused records are `could_not_act`. EC-W19 (b) and (c) require "not matching" for a refusal the page cannot reproduce. A deliberately refused `ClosePosition` followed by price recovery shows "Could not act". Test: refused close plus recovery must not be better than unverifiable.
- **An invalid record that both providers agree on is only "unverifiable" (security M2).** `run.ts:101-109`. EC-W05 wants "not matching"; keep "unverifiable" only for provider failure or disagreement.
- **More than 64 records skips later checks (security M3).** `run.ts:206` returns early, so a changed code hash or key can no longer surface. Add a row and continue; test 65 records plus a changed hash.
- **The deploy-block baseline is tautological (security M4).** `checkAccountIntegrity(pairs, key, pairs[0].block)` (`run.ts:243`, `account.ts:46`) can never fail; snapshot blocks come from the source, not the chain (EC-W29, EC-W16).
- **parseState validation (rules-verifier M1).** `num` accepts any number; `closedBy` is cast unchecked (`run.ts:57-73`). Export the rules' state validator.
- **Missed-close inputs (rules-verifier M2, test M-T5).** A pending close (`resultBlock === null`) is dropped from the closes but counted as a lock (`run.ts:225-227`); `ExitRemove` handling and Refused/Failed as locks are guesses; the `window_count` bound and an unreadable `get_limits` are untested.
- **`decisionMatchesRecord` is half a check (rules-verifier M3, test M-T4).** Only kind and range; `ExitRemove` returns `true`; `left_point` and `observed.point` comparisons survive mutation.
- **Test gaps that decide Matching vs Not matching (test M-T1 to M-T3, M-T6).** EC-W14 only tests a wrong pool (rogue DCL contract or quote token survive); the code hash can be accepted from one provider (`run.ts:244`); the status row is "matching" for any state (`run.ts:190`, no Running/Open/Closing/Cancelled test); `len >= 64` vs `> 64` not tested at 64.
- **Claims table (claims-checker).** `EC-W15` (reproducible-build mismatch) is cited as evidence for the providers-disagree claim, yet the README says a reproducible build is not checked; `run.test.ts` does name EC-W15 (the audit session checked), but for the pin-differs case, so the citation does not fit the sentence. Trim the list to IDs that fit ("does not show Matching when rules, records, providers or samples fail to check").
